# Stripe Payment Flow — Hardening Plan

**Status**: Phases 1 & 3 implemented. Phase 2 (`invoice_creation`) intentionally
skipped — see decision note below. NIP capture is enabled so a KSeF-compliant
faktura can be issued out-of-band for B2B buyers.

**Decisions taken**
- Customer objects are created **lazily at first purchase** (not at signup).
- Billing address is **optional** (`billing_address_collection: 'auto'`).
- NIP is **optional** (`tax_id_collection: { enabled: true }`).
- `invoice_creation` is **off**: a Stripe invoice is not KSeF-compliant for B2B,
  and B2C sales don't legally require a faktura — so it buys nothing and adds a
  0.4% fee. Free Stripe email receipts cover B2C; real B2B faktury go through a
  KSeF tool as a future task.
**Problem**: Payments succeed, but buyers don't appear as Customers in the Stripe Dashboard — only "Guest" entries. Root cause: Checkout Sessions are created without `customer` / `customer_creation`, and since Stripe API 2022-08-01 the default in `mode: 'payment'` is `customer_creation: 'if_required'`, which creates **no** Customer object for plain one-time card payments.

---

## How top SaaS players model this

The industry-standard pattern (used by virtually every serious SaaS on Stripe):

1. **One Stripe Customer per app account, created lazily at first purchase** (or at signup), never per-transaction.
2. **`stripeCustomerId` stored in your own database** as the single source of truth for the mapping.
3. **Every Checkout Session passes `customer: cus_xxx`** — so all payments, invoices, receipts, and saved payment methods accumulate on one Customer.
4. **Tax ID + billing address collected in Checkout** when invoices matter; invoices auto-generated by Stripe.
5. Webhooks treat `session.customer` as the durable link, with `client_reference_id` / `metadata.userId` as the app-side correlation.

We already have Clerk as the identity system, so this maps 1:1 (Option 2 from the issue summary — the recommended one).

## Phase 1 — Customer object per user (the core fix)

### 1.1 Schema: store the mapping

Add to `users` table in `src/server/db/schema.ts`:

```ts
stripeCustomerId: varchar("stripeCustomerId", { length: 256 }).unique(),
```

Run `pnpm run db:push`.

### 1.2 `getOrCreateStripeCustomer(userId)` helper

New server-side helper (e.g. `src/server/stripe.ts`):

1. Look up `users.stripeCustomerId` — if present, return it.
2. Otherwise fetch the Clerk user (email, full name) and call:

```ts
stripe.customers.create(
  {
    email,
    name,
    metadata: { userId },       // Clerk userId — makes Dashboard ↔ app lookup trivial
  },
  { idempotencyKey: `customer-create-${userId}` }  // guards double-click races
)
```

3. Persist `cus_...` to the `users` row, return it.

Lazy creation means existing users get backfilled naturally on their next purchase — no migration script needed.

### 1.3 Checkout Session changes (`src/actions/stripe.ts`)

```ts
const customerId = await getOrCreateStripeCustomer(userId)

const session = await stripe.checkout.sessions.create({
  customer: customerId,
  customer_update: { address: 'auto', name: 'auto' },  // required so Checkout saves collected address onto the Customer
  billing_address_collection: 'auto',
  // ...existing params unchanged (line_items, mode, urls, client_reference_id, metadata)
})
```

Note: `customer_update` can only be sent when `customer` is provided, and without it Stripe rejects sessions that try to collect addresses for an existing customer.

### 1.4 Webhook (`src/app/api/webhooks/stripe/route.ts`)

- Read `session.customer` and **backfill** `users.stripeCustomerId` if the row doesn't have one yet (covers sessions created before deploy, or any future path that used `customer_creation`).
- Extend `stripe_payments` with `stripeCustomerId`, `sessionId`, and `paymentIntentId` columns — today the table has no key back to Stripe, which makes refunds/support lookups painful.

## Phase 2 — Invoices & address ("faktura")

### Is address collection needed?

For **Polish B2C** sales a payment receipt is legally sufficient; a faktura is only required for B2B (NIP) or when a consumer requests one. So a full address is *not* required to take payment — but it is required to issue a proper invoice. Recommended setup:

```ts
billing_address_collection: 'required',   // full address → valid invoice data
tax_id_collection: { enabled: true },     // optional NIP field (shown as eu_vat for PL buyers)
invoice_creation: { enabled: true },      // Stripe auto-issues a post-payment invoice PDF
```

- `tax_id_collection` shows an *optional* "I'm purchasing as a business" toggle — consumers can skip it, companies enter their NIP. Zero friction for B2C.
- `invoice_creation` gives every buyer a downloadable invoice/receipt automatically. **Cost: 0.4% of the transaction, capped at ~2 USD per invoice** (Stripe Invoicing fee for post-payment invoices). If that fee is unwanted, skip it and rely on Stripe email receipts (free — enable in Dashboard → Settings → Emails → "Successful payments").

### ⚠️ KSeF caveat (Poland, 2026)

Since **April 1, 2026** all Polish VAT-registered businesses must issue **B2B** invoices through KSeF (Krajowy System e-Faktur). Stripe-generated invoices are **not** KSeF-compliant. However:

- **B2C invoices are exempt** — KSeF is voluntary for consumer invoices, with no mandatory date planned.
- If Wolfmed sells mostly to individual students (B2C), Stripe `invoice_creation` is fine as-is.
- For genuine B2B sales (buyer provides NIP), the compliant faktura must be issued via a KSeF-integrated tool (Fakturownia / inFakt / wFirma — all have APIs). The clean pattern: in the `checkout.session.completed` webhook, if `customer_details.tax_ids` is non-empty, push an invoice to the KSeF tool. This is a **separate follow-up project** — don't block Phase 1/2 on it.

**Recommendation**: enable `billing_address_collection: 'required'` + `tax_id_collection` now (data costs nothing and future-proofs B2B), decide on `invoice_creation` based on the 0.4% fee tolerance, and treat KSeF integration as its own task if/when B2B volume appears.

## Phase 3 — Flow hygiene (found during review)

1. **Remove or auth-gate `/api/stripe/create-checkout-session`** (`src/app/api/stripe/create-checkout-session/route.ts`). It's unauthenticated and trusts `userId` from the request body — anyone can mint sessions with an arbitrary `client_reference_id`. The live path is the `createCheckoutSession` server action; the route appears referenced only in docs. Delete it.
2. **`insertPayment` failures are swallowed** in the webhook (logged, then processing continues). Consider returning 500 so Stripe retries — the existing `processedEvents` idempotency check makes retries safe.
3. **`locale`**: Checkout auto-detects, but `locale: 'pl'` can be pinned for a consistent Polish checkout.
4. **Future**: if courses are ever sold outside Poland, look at Stripe Tax (`automatic_tax`) for EU VAT OSS — pairs naturally with the Customer + address data from Phases 1–2.
